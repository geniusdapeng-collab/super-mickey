## 2026-06-18 09:00 - PromptForge Stage-12 反复卡死深度分析

### 现象
- patch14（双层超时保护）两次卡死
- patch15（缩短单调用超时至3分钟）再次卡死
- Stage 2a（编剧台词）卡住15分钟后被全局超时强制退出
- CPU 0%, 进程状态 Sl（可中断睡眠），fd 21 持有 socket

### 根因
Node.js `fetch` + `AbortController` 在连接建立后的数据传输阶段，若服务端无响应，AbortController 发出的 abort 信号无法让 fetch Promise 立即 reject。这导致 Promise.race 的外层 setTimeout 也无法触发——因为两个 Promise 都挂住了。

**本质**：底层 HTTP 连接一旦建立，JavaScript 层的超时机制全部失效。

### 已尝试但失败的方案
1. AbortController + setTimeout（_fetchWithTimeout）—— 失败
2. Promise.race + setTimeout（patch14）—— 失败  
3. 缩短 timeoutMs 至 3 分钟（patch15）—— 失败

### 对话记录
- 李大鹏："太糟了！又卡住了！"
- 李大鹏："根因找到没有？"
- 李大鹏："那改3分钟是不是太少了？"
- 李大鹏："这他妈又卡死了！"

### 教训
不要依赖 Node.js fetch 的超时机制处理网络阻塞。应考虑：
1. 改用主进程直接调用 LLM，避免子进程隔离
2. 使用 spawn + kill -9 强制终止
3. 或在 HTTP 层使用更底层的库（如 got/axios with timeout）
